## 0. 结论摘要

| # | 结论 | 影响 |
|---|---|---|
| 1 | Pose2Arm 输出 **18 维人体臂几何 + 14 维关节角**，可用 | 动作迁移主链路成立 |
| 2 | Pose2Arm **完全不产出手部关键点**，全仓搜 `hand` 零命中 | **任务书的夹爪双阈值迟滞无法实现**，见 §4.1 |
| 3 | 左右臂顺序两端口径一致，可直接对位 | 无隐藏换算 |
| 4 | OpenArm 动作向量 **18 维**，比 Pose2Arm 的 14 维多 4 个手指维 | 手指那 4 维**没有来源**，与第 2 条同源 |
| 5 | 基础场景现有 5 路相机；冻结 wrapper 另加 1 路**单目 90° 顶视**工作区相机 | 当前交付链路只读取 `workspace_camera`，见新接口说明 |
| 6 | **左右夹爪 actuator 类型不同**：右=位置伺服，左=力矩电机 | 单臂任务固定使用右臂；实测夹持力见 §2.4 |

**一句话**：手臂链路是通的；**夹爪链路现在是断的**，且这是阶段一必须拍板的头号阻塞项。

## 1. Pose2Arm 输出侧

### 1.1 落盘产物

链路：`extract_pose.py` → `retarget.py` → `generate_ik_dataset.py` / `scripts/rerun_ik.py`
产物为单个 npz（本机样例：`pose2arm-main/data/p2a_test.npz`）。

| 键 | 形状 | 含义 |
|---|---|---|
| `target_obs` | `(2N, 18)` | 每帧人体臂几何，见 §1.2 |
| `joint_angles` | `(2N, 14)` | 反解出的机械臂关节角（rad），见 §1.3 |
| `frame_indices` | `(2N,)` int | 对应源视频帧号 |
| `fps` | 标量 | 源视频帧率 |

**布局**：`[0:N]` = 原始片段，`[N:2N]` = 镜像片段（左右互换），两段都按时间序。
镜像段是数据增广，**不是**额外的真实动作。

### 1.2 `target_obs` 的 18 维

每臂 9 维 = 3 段 × 3 分量，全部是**单位方向向量**，不是位置、不是关节角。

| 索引 | 含义 |
|---|---|
| `0:3` | 左 · 上臂方向 |
| `3:6` | 左 · 前臂方向 |
| `6:9` | 左 · 臂平面法向（伪向量） |
| `9:12` | 右 · 上臂方向 |
| `12:15` | 右 · 前臂方向 |
| `15:18` | 右 · 臂平面法向（伪向量） |

坐标系为**人体躯干坐标系**（由 MediaPipe 世界点构造）。`retarget.py` 内部再做一次
映射到机械臂基座坐标系；映射参数未导出到 npz，`[未验证]` 是否可离线复现。

### 1.3 `joint_angles` 的 14 维

`joint_angles[:, :7]` = **左臂** j1–j7，`joint_angles[:, 7:]` = **右臂** j1–j7。
依据：`generate_ik_dataset.py:335-337` 为 `concatenate([joints_l, joints_r], axis=1)`。

> 该顺序与 OpenArm 动作向量（§2.2）一致，**可直接对位，无需左右交换**。
> `rerun_ik.py:61-62` 的 warm start 左右交叉是**故意**的（镜像段左右互换），不是缺陷。

### 1.4 上游关键点来源

`extract_pose.py` 使用 MediaPipe **BlazePose，33 点人体**：

- `pose` `(T, 33, 4)` —— 归一化图像坐标，仅用于画叠加视频
- `pose_world` `(T, 33, 4)` —— **米制**，原点在髋中点，几何计算用这个
- `pose_present` `(T,)` bool —— 该帧是否检出人体
- `fps` 标量

配 One Euro 滤波（`smoothing.py`）去抖。

**33 点里只有手腕（15/16），没有拇指尖、没有食指尖。**

## 2. OpenArm 仿真控制侧

### 2.1 场景与驱动入口

| 项 | 值 | 出处 |
|---|---|---|
| 双臂模型 | `simulation/v1/openarm_bimanual.xml` | — |
| 驱动脚本 | `teleop_towel_dataset.py` | — |
| 控制频率 | **20 Hz**（`--control-hz` 默认 20） | `teleop_towel_dataset.py:820` |

### 2.1.1 控制量是两段式 —— 臂和指不是同一种控制

**这是最容易踩的坑。**

| 部位 | actuator 类型 | `data.ctrl` 的含义 | 范围 |
|---|---|---|---|
| 臂 j1–j7 | `motor`（**直接力矩**） | **力矩** N·m | ±40（DM8009）/ ±27（DM4340）/ ±7（DM4310） |
| 右手指 ×2 | `position`，`kp=100` | **目标开度** m | `0 .. 0.044` |
| 左手指 ×2 | **`motor`（力矩）**，增益 1.0 | **力** N | ±333 |

⚠️ **手指左右不对称** —— 详见 §2.4，这是本场景的一个缺陷，不是笔误可略过的细节。

`apply_controller()` 把 18 维 **action 向量**落成 `data.ctrl`：

- **臂**：action 的 7 维是**关节角目标**（rad），**不是** ctrl 值。经重力补偿 PD 转力矩：

  ```python
  torque = data.qfrc_bias[spec.dof] + kp*(q_target - q) - kd*qvel
  data.ctrl[actuator] = clip(torque, actuator_forcerange)
  # kp = [80,80,55,55,25,20,20]   kd = [8,8,5,5,3,2,2]
  ```

- **手指**：action 的 2 维**直接就是**位置目标，不经 PD。

**推论**：episode 记录的「目标动作」是**关节角**，而真正下发给仿真的 `ctrl` 是**力矩**，
两者不是同一个量，换算需要 `q` / `qvel` / `qfrc_bias`（见 `dataset_schema.md` §6.3）。
用 `ctrl` 当模仿学习的 action 目标会用错量纲。

### 2.2 动作向量（18 维）

| 索引 | 含义 |
|---|---|
| `0:7` | 左臂 j1–j7 目标角（rad） |
| `7:9` | 左手指关节（m，两指同值） |
| `9:16` | 右臂 j1–j7 目标角（rad） |
| `16:18` | 右手指关节（m，两指同值） |

依据：`apply_controller()`，`base = 0 if side == "left" else 9`。

### 2.3 关节限位（rad）

| 关节 | 左臂 | 右臂 |
|---|---|---|
| j1 | `-3.490659 .. 1.396263` | `-1.396263 .. 3.490659` |
| j2 | `-3.316125 .. 0.174533` | `-0.174533 .. 3.316125` |
| j3 | `-1.570796 .. 1.570796` | 同左 |
| j4 | `0.0 .. 2.443461` | 同左 |
| j5 | `-1.570796 .. 1.570796` | 同左 |
| j6 | `-0.785398 .. 0.785398` | 同左 |
| j7 | `-1.570796 .. 1.570796` | 同左 |

j1/j2 左右**互为镜像**（符号翻转），j3–j7 完全相同。
关节名：`openarm_{left,right}_joint{1..7}`。

### 2.4 夹爪 —— 左右不对称（本场景缺陷）

关节行程 `0.0 .. 0.044` m（`openarm_{side}_finger_joint{1,2}`），
`0.000` = 闭合、`0.044` = 张开，脚本默认 `0.020`；同一个值写给两指（非独立控制）。

XML 里两侧 actuator 用了**不同元素类型**（`openarm_bimanual.xml:345-346` 对 `354-355`）：

```xml
<motor    name="left_finger1_ctrl"  joint="openarm_left_finger_joint1"  class="motor_finger" />
<position name="right_finger1_ctrl" joint="openarm_right_finger_joint1" class="motor_finger" />
```

MuJoCo 3.8.1 实测确认（`nq=25 nv=24 nu=18`）：

| | 左手指 (7,8) | 右手指 (16,17) |
|---|---|---|
| `actuator_biastype` | `none` | `affine` |
| `actuator_gainprm[0]` | `1.0` | `100.0` |
| `actuator_biasprm[:3]` | `[0, -100, 0]`（**被忽略**） | `[0, -100, 0]` |
| 实际语义 | `力 = 1.0 × ctrl` | `力 = 100 × (ctrl − q)` |
| `ctrl=0` 时的力 (q=0.03) | **0.000 N** | **−3.0 N** |

**动态实测**（从全开 q=0.044 出发，指令闭合）：

| 侧 | 2 s | 5 s | 10 s |
|---|---|---|---|
| 左 | 0.02675 | 0.01259 | 0.00359 |
| 右 | 0.00176 | 0.00176 | 0.00176 |

**结论**：

- 两只夹爪**都能张能合**，行程相近（约 40 mm）。
- **左臂没有主动闭合力**：`ctrl=0` 恰好等于零力，手指仅靠关节被动弹簧
  （`stiffness=0.5`、`damping=2`）缓慢合拢，时间常数约 **4 s**，在 30 mm 处约 **0.006 N**。
- **右臂是位置伺服**，`ctrl=0` 时在 30 mm 处可施加 **3 N** 闭合力。

**能不能拿住方块**：方块的 `droid_object` 质量 0.18 kg、指-块摩擦 μ=1.0，
理论上每指需要 `mg/(2μ) = 0.883 N` 法向力。冻结场景中右夹爪纯摩擦抓取的
**真实接触法向力实测合计 6.123 N**；标准任务中方块抬升 117.5 mm、最大姿态
变化 2.25°，全程没有 weld。左臂 `ctrl=0` 仍只有约
0.006 N，差两个数量级，
因此单臂任务固定使用右臂。

> 这些是早期原始 actuator 的记录；历史 6.123 N 是接触法向力合计，不与交接文档 6.085 N 的夹持力测量混为同一项。交接实测 6.085 N 对应每指约 3.043 N、相对理论需求约 3.4 倍。当前 B 场景已在编译后修复左指位置伺服，任务依然固定右臂；本次 NPZ 夹爪全程打开，没有重新测量抓取夹持力。

**独立旁证**：用 `handeye_grasp_red_cube.py` 的 `search_reachable_grasp` 在**左臂**
能找到 2.3 mm 精度的可达抓取位姿，但合爪后 `grasp_contact_status` 报
**零个指-块接触**、方块抬不起来 —— 与上述分析同因。

⚠️ **阶段一冻结场景时必须先定：用右臂当执行臂，或者修掉左侧 actuator。**
不要把一个"左臂抓不住"的场景原样冻结进任务定义。

> 另注：任务书要求的双阈值迟滞是**状态机**行为，
> 应实现在控制层（把 D 映射成 `0.000` / `0.044`），而不是靠 actuator 自身。

## 4. 阻塞项

### 4.1 夹爪控制输入缺失（P0，A+B 共同）

任务书规定：

```
D = 食指与大拇指尖欧氏距离
D < 2.5 cm        → 闭合
D > 4.5 cm        → 张开
2.5 ≤ D ≤ 4.5 cm  → 保持上一帧（防抖）
```

**当前 Pose2Arm 链路产不出 D。** 全仓（`pose2arm-main/**/*.py`，忽略大小写）搜 `hand`
只命中 3 处英文散文（"hand-crafted"、"a hand held still"、"to handle"），
无任何手部追踪代码；`extract_pose.py` 只有 BlazePose 33 点。

可选解法（阶段一需定，属 A 的决策范围）：

| 方案 | 做法 | 代价 |
|---|---|---|
| a. 加 MediaPipe Hands | 在 `extract_pose.py` 旁挂一路 21 点手部检测，取 4 号点（拇指尖）与 8 号点（食指尖）算 D | 新增一次前向；需处理手部与人体检测的帧对齐 |
| b. 改判据 | 不用指尖距离，改用其他可得的开合信号 | **偏离任务书**，需报备 |
| c. 手工/键盘 | 阶段一先用键盘 G/H 代替，管线通了再换 | 只能支撑阶段二，不能支撑阶段三实时 |

**建议 a**，且越早越好 —— 整个夹爪链路和「人机演示一致性」的论证都压在这上面。

### 4.2 相机布置（P1，冻结场景时处理）

任务书：**单目摄像头，正面或斜上方 45° 俯视，人手完全入画**。
基础场景实际有 5 路：`front_camera`、`side_camera`、`v22_left_d405_rgb`、
`v22_right_d405_rgb`、`chest_d435i_preview`。冻结 wrapper
`droid_cube_scene_perception.xml` 另加第 6 路 `workspace_camera`，固定在工作区
正上方、90° 顶视；B 单目延迟测试只读取这一相机。真实人体采集用独立 USB 摄像头，任务书的正面/45° 要求针对人体采集，不能拿仿真顶视方块相机冒充。胸部/腕部相机仍参与另一个自主 RGB-D 抓取演示模式。
