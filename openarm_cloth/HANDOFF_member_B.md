## 4. 按顺序做了什么

### 4.1 冻结单臂抓取场景

`droid_cube_scene.xml` 是团队的冻结场景，且**不能就地改**——`build_droid_object_scene.py:ensure_scene()`
会在 mtime 对不上时把它从 `folding_scene_V25_4_TOWEL_SUPPORT_04.xml` 静默重新生成。

做法：写一个薄包装 XML，`<include>` 原场景 + 追加一个固定单目相机，编译后把模型里能读到的物理参数
全部倒进配置 JSON，并把原场景的 sha256 记进配置。`--verify` 可以检测原场景是否被人动过。

### 4.2 单目摄像头识别

红掩码 → 轮廓拟合，在桌面上解 x / y / yaw 三个未知量，用与掩码的真实 IoU 打分。

原实现 210.8 ms，太慢。改成**向量化解析排序**：一次性投影 N 个候选位姿的 8 个角点
（`np.einsum`），用鞋带公式 + `argsort`/`take_along_axis` 解析地算凸包面积与质心，最后仍用
**真实 IoU 复评分**选出赢家——所以这是纯加速，结果与优化前逐位相同。

**210.8 ms → 21.5 ms，误差 2.24 mm，IoU 0.9726（拟合）/ 0.9544（真值）。**

### 4.3 纯摩擦抓取标定（核心）

**发现的致命问题**：`search_reachable_grasp()` 遍历 6 个带符号世界轴
（`for axis in range(3): for sign in (-1, +1)`），保留 IK 残差最低的那个。但**赢的轴会在不同调用间翻转**：
实测先是 `y−` 残差 18.1 mm，目标一移动就变成 `y+` 9.8 mm。不同符号的轴互为镜像，
所以任何跨调用累积的修正都会失效。这也解释了同一个计划为什么有时 2 个接触点、有时 0 个。

**修法：钉死轴 + 接触质心重定位。** 闭合一次 → 在方块**自身坐标系**里读接触质心
（`R.T @ (contact_pos − cube_pos)`）→ 把请求的抓取中心按负质心平移 → 重新规划。
5 次迭代，从偏离 37.0 mm 收敛到 4.2 mm。

**重要**：这 5 趟循环是**离线标定程序，不是执行路径**（5 × 8 s 远超任务书的 15 s 预算）。
结果烘焙进配置：轴 `y-`，偏移 `[-48.0, 5.3, 25.2]` mm。执行时直接读回来，一趟完成。

**摩擦力从来不是限制**：实测夹持力 6.085 N（每指 3.043 N），而 `2μN ≥ mg`
（μ=1.0, m=0.18 kg）只需 0.883 N/指 → **3.4 倍余量**。

### 4.4 Pose2Arm 接入执行器

**契约陷阱**：`joint_angles[:, 0:7]` 是**左臂**在前，与文件里
`JOINT_NAMES = RIGHT_JOINT_NAMES` 的列出顺序**相反**。用关节限位反推证明的——
第 0 列数据能到 −3.2960 rad，而右臂 joint1 下限是 −1.3963、左臂才到 −3.4907，所以只有「左臂在前」成立。
写了 `verify_joint_order()`，每次加载都重新推导，推不出来就拒绝驱动，绝不猜。

**第二个发现**：Pose2Arm 完全不输出手部数据 → 任务书的夹爪迟滞规则（D<2.5 cm 闭合 / D>4.5 cm 张开 /
中间保持）没有人类侧输入。按用户选定方案，D 改从仿真侧取：**夹爪钳口中点到单目感知物体中心的距离**。
（钳口中点用两个手指**碰撞**几何体的原点均值；注意指体是 MESH，其原点离接触面很远，EE body 原点更远，
实测差 80 mm。）

**第一次实跑在第 9 帧紧急停止。** 查下来不是限幅器的问题，是**源数据本身超速**：
`p2a_test.npz` 单帧最大跳变 R1 = 3.279 rad（20 Hz 允许 0.838，即 3.9 倍；30 fps 允许 0.559，5.9 倍），
R3 = 2.643 rad（9.7 倍 / 14.5 倍）。→ 把限幅改成**正常工作模式**（夹住是常态，不是错误），
紧急停止只留给 `RATE_GLITCH_MULTIPLE = 20x` 的数据毛刺。**这是成员 A 的源数据问题，驱动侧修不了，需要反馈。**

**762 帧完整跑通**，无急停；42 帧被限速；最大跟踪滞后 2.353 rad；97.3 s 墙钟（7.8 fps）。
夹爪全程未闭合（762 帧里 D > 4.5 cm）。

**修的内存泄漏**：`perceive()` 不传渲染器时会自己新建并关闭 GL 上下文，等于每帧泄漏一个；
进程涨到 1.9 GB 还没跑完。改成整个运行复用一个 `mujoco.Renderer`，`try/finally` 里关闭。

### 4.5 单次抓取执行

`demo_grasp_viewer.py`：把 5 趟标定循环压成「读烘焙偏移 + 一趟 接近 → 下降 → 闭合 → 抬起」。
每次运行**重新推导抓取轴并与配置交叉校验，不匹配就拒绝运行**——因为轴一翻转，烘焙偏移就静默作废了。

无头验证（`--check`）：**LIFTED +95.1 mm**，2 个接触点，6.085 N，垫片偏离物心 3.9 mm，侧移 2.3 mm。全程无 weld。

配套 cv2 窗口：实时显示原始画面 + 红色掩码 + 绿色拟合轮廓 + 青色投影角点 + 文本
（坐标 / yaw / IoU / 距离 → 开合状态）。

### 4.6 实时采集与延迟测量

`realtime_capture.py` 跑的是**真实控制 tick**（render → mask → fit → gripper → actuators → physics），
不是模拟；用的是 `workspace_camera.perceive`、`pose2arm_driver.GripperHysteresis`、
`teleop_towel_dataset.apply_controller`。唯一强制的是**臂的姿态保持不变**——测的是这一 tick 的开销，
不是一次 reach。

**「端到端」的精确定义**：从请求相机帧，到消耗了该帧夹爪指令的物理步完成。
**不含**仿真启动和 GL 上下文创建（这两项单独报告，把启动开销算作每帧延迟是往好看方向的撒谎）。

加了**机器负载指数**（固定 FFT 负载计时）：这台机器的时间会随别的进程摆动 3–5 倍，
没有这个指数，日志无法跨运行比较。报告原始毫秒值，**不给比值**（本机没有可测的空闲基线）。

**结果见 `outputs/20261014/latency_log.json`（120 帧版）**：端到端 65–66 ms，20 Hz 预算 50 ms，
`budget_verdict: FAIL`，三次运行一致（实际 15.2 Hz）。瓶颈是拟合（48–49 ms）。

## 5. 已知的坑（接手前必读，否则会重踩）

1. **`python` 命令是死的**——退出码 49、零输出。用 `/d/miniconda3/envs/openpi/python.exe`。
2. **MuJoCo 相机的朝向符号**：相机沿自身 **−z** 看，所以 `mju_quatZ2Vec(q, …)` 要传
   **`camera − target`**，不是 `target − camera`。传反了会渲染出**全黑画面且不抛任何异常**。
   只靠渲染自检（亮像素占比 < 1% 就拒绝）能抓到，读四元数是抓不到的。
   自由相机同理：**elevation −25 → 相机在上方往下看（z=0.892）；+25 → 在下方往上看（z=−0.122）**。
3. **`MjvCamera` 上没有 `cam.pos` 属性**，读了得到 (0,0,0)。位置要在 `mjvUpdateCamera` 之后
   从 `sc.camera[0].pos` 读。
4. **自由相机不设 `lookat` 会瞄模型中心**——本场景工作区不在模型中心，于是抓取跑到画面外一边，
   看起来像「对着空气夹」。每次 sync 时 `cam.lookat[:] = d.xpos[object_body]`。
5. **抓取轴会翻转**（见 §4.3），任何跨调用的修正都必须先钉死轴。
6. **`%TEMP%\perceive.py` 的 `make_scene()` 会覆盖**
   `simulation/v1/droid_cube_scene_perception.xml`。该 wrapper **没有 sha256 保护**（只有基础场景有）。
   跑过那个临时脚本，冻结的相机配置就会被静默换掉。
7. **`LAST_PROFILE.clear()` 会让埋点值变成每帧值**——我因此一度报出「各阶段之和约 1.27 ms」的错数，
   真实拆分是向量化约 18 ms + 精修约 24 ms。做性能埋点时注意这一点。
8. **抖动诊断**：接触点落在方块的**棱**上（不是面上）时只有 2 个接触点。两个点能抵抗平移，
   **抵抗不了绕接触线的转动**——方块会绕那根棱摆。这跟摩擦力大小无关。
